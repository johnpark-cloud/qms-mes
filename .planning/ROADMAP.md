# Roadmap: QMS+MES (localhost)

## Overview

기록 화면의 공통 틀과 검사 상세를 먼저 새로 만들고(B0), 모듈 켜기/끄기를 인터록이 약해지지 않는 방식으로 깐 다음(A1·A3·A4), Django 관리 화면에만 있던 기록을 서버 기록 설명서 하나로 그리는 React 화면으로 하나씩 옮긴다(B1~B6). 모듈 대응표가 먼저 있어야 B1 이후에 새로 생기는 경로가 모두 대응표에 등록되고, 종결 허용이 먼저 있어야 화면을 옮기는 도중에 풀 수 없는 인터록이 생기지 않는다. 라이선스·패키지는 본인 전용 시스템이라 범위에서 뺐다(2026-11-13). 모듈 행이 없으면 켜진 것으로 보므로 데이터 마이그레이션은 없다.

## 모든 단계 공통 완료 조건

아래를 모두 만족해야 단계가 끝난다. 단계별 성공 기준에는 다시 적지 않는다.

- `manage.py test`(PostgreSQL), `scripts/e2e_check.py`, `makemigrations --check --dry-run`이 통과한다.
- 기존 인터록 테스트(LOT 보류, 부적합 처분, 검사 판정, 계측기 교정, 4M·SPC)가 하나도 빠지지 않고 통과한다.
- 프런트를 바꿨으면 `npm run build` 후 `frontend/dist`를 같은 커밋에 넣는다.
- Phase 5부터: 새로 생긴 경로는 모듈 대응표에 등록되어 MOD-02 테스트를 통과하고(REC-13), 옮긴 모델의 관리 화면 변경 페이지에 「새 화면으로」 링크가 있다(REC-12).
- 실행하지 않은 검증은 통과했다고 보고하지 않는다.

## Phase Details

### Phase 1: 기록 화면 공통 틀과 검사 상세 (B0)
**Goal**: 사용자는 모든 React 기록 상세에서 같은 배치를 보고, 검사원은 검사 상세에서 판정과 측정 결과를 한눈에 읽는다
**Mode:** mvp
**Depends on**: Nothing (first phase)
**Requirements**: SHELL-01, SHELL-02, SHELL-03, SHELL-04, SHELL-05, SHELL-06, SHELL-07
**Success Criteria** (what must be TRUE):
  1. 품번·검사기준·관리계획서·검사 상세를 열면 모두 머리 띠 + 기본정보 4열 + 본문 + 오른쪽 열 배치로 보이고, 버튼이 「주요 1개 · 이력 · ⋯ 메뉴」 순서이며 삭제(또는 삭제 요청)는 「⋯」 메뉴 한 곳에만 있다
  2. 검사 상세 맨 위에 28px 판정 띠가 합격·불합격·미판정을 색과 글자로 함께 보인다
  3. 측정값 표의 한 줄에 하한·기준(중앙)·상한·단위·측정값·위치 막대·판정·계측기가 보이고, 숫자는 규격 자릿수로 맞춰져 있으며 판정은 서버 판정과 일치한다
  4. 검사 상세에 공급사·입고 수량·샘플링·검사기준 승인자·연결 CAPA가 보이고, 상세 API의 기존 키는 그대로다
  5. 390px 폭에서 오른쪽 열이 본문 아래로 내려가고 라이트·다크 모두 토큰 색으로 보이며, DESIGN.md에 「기록 화면 규칙」이 있다

### Phase 2: 모듈 대응표와 켜기/끄기 게이트 (A1)
**Goal**: 시스템 관리자가 모듈을 켜고 끄면 꺼진 모듈의 화면·API가 일반 사용자에게 닫히고, 기본 플랫폼은 끌 수 없다
**Mode:** mvp
**Depends on**: Phase 1 (순서상. 기술적으로는 독립)
**Requirements**: MOD-01, MOD-02, MOD-03, MOD-04, MOD-05, MOD-09
**Success Criteria** (what must be TRUE):
  1. 시스템 관리자는 모듈을 켜고 끌 수 있고, 행이 없는 모듈은 켜진 것으로 보인다. 품질팀장을 포함한 다른 역할이 바꾸려 하면 서버가 거부한다
  2. 모듈을 끄면 일반 사용자는 그 모듈의 화면·API에서 404를 받고, 시스템 관리자는 조회(GET)만 된다
  3. 꺼진 모듈은 메뉴와 `me` 응답에서 빠지고, React에서 그 경로를 열면 「비활성 모듈」 안내가 보인다
  4. 필요한 모듈이 꺼져 있으면 켜기가 거부되고, 켜진 다른 모듈이 필요로 하는 모듈은 끄기가 거부된다
  5. 부적합·보류·LOT·기준정보·시스템은 끌 수 없고, 어떤 모듈 설정에서도 LOT 보류 인터록이 그대로 동작한다. 모듈 대응표에 매핑되지 않은 URL 패턴이 하나라도 있으면 테스트가 실패한다

### Phase 3: 끄기 전 열린 기록 검사와 종결 허용 (A3)
> **착수 전 결정 (미결 #3)**: 검사 모듈이 꺼졌을 때 4M 초품 해제 경로. 해제 수단이 검사 판정뿐이라 `qms_inspection`이 꺼지면 해제할 길이 없다. 시스템 관리자에게 검사 판정을 허용할지, 수동 해제 규칙을 신설할지 정한다. 둘 다 업무 규칙 변경이므로 사용자 승인이 먼저다.

**Goal**: 모듈을 끄는 일이 풀 수 없는 인터록을 만들지 못하고, 끈 뒤에도 시스템 관리자가 열린 기록을 닫아 인터록을 풀 수 있다
**Mode:** mvp
**Depends on**: Phase 2
**Requirements**: MOD-06, MOD-07, MOD-08
**Success Criteria** (what must be TRUE):
  1. 열린 기록(미종결 CAPA, 초품 합격 전 4M, 미종결 클레임·SCAR·심사, 미승인 PPAP, 미판정 검사, 열린 작업지시)이 있는 모듈을 끄려 하면 거부되고 해당 기록의 번호 목록이 보인다
  2. 모듈이 꺼진 뒤에도 시스템 관리자는 CAPA·클레임·SCAR·심사 종결과 4M 초품 판정 기록으로 열린 기록을 닫을 수 있고, 닫으면 그 기록이 걸던 인터록이 풀린다
  3. 꺼진 모듈에서 종결 화이트리스트 밖의 쓰기는 403이다
  4. 인터록 거부 메시지에 원인 모듈과 기록 번호가 붙고(예: `[4M 변경] CR-…`), 모든 모듈을 끈 상태에서도 부적합 등록 → 보류 → 투입·실적·출하 차단 규칙은 바뀌지 않는다

### Phase 4: 꺼진 모듈 소비처 필터와 클레임 설정 이동 (A4)
**Goal**: 꺼진 모듈의 기록이 할 일·알림·위젯 같은 일상 화면에서 조용히 빠지되, 추적 화면에서는 건수로 남고, 클레임 설정이 제자리를 찾는다
**Mode:** mvp
**Depends on**: Phase 2, Phase 3
**Requirements**: MOD-10, MOD-11, MOD-12, MOD-13
**Success Criteria** (what must be TRUE):
  1. 모듈을 끄면 그 모듈의 기록이 내 할 일·기한·알림 메일·위젯·종합현황에서 사라진다
  2. LOT 이력·검색·연결 패널은 꺼진 모듈 기록을 감추지 않고 「비활성 모듈 기록 N건」으로 보인다

  4. 고객사별 8D 기한 설정이 메뉴 「고객 클레임 › 클레임 설정」에 있고, `qms_claim`을 끄면 함께 사라진다

### Phase 5: 기록 설명서와 records API, 첫 4종 이전 (B1)
> **착수 전 결정 (미결 #6)**: 기록별 변경 이력(감사 기록) 탭을 누구에게 보일지. 기존 `/api/audit-log/`는 품질팀장 전용이다. 상세 화면의 이력 탭을 모델 `view_` 권한 기준으로 열지, 품질팀장 전용으로 둘지 정한다. 보안·정보 노출 정책이므로 사용자 승인이 먼저다.
>
> 설명서의 틀·레지스트리는 `core/recordspec.py`에 둔다. `core/records.py`는 삭제·잠금 규칙이 이미 들어 있어 건드리지 않는다(PROJECT.md B1의 `core/records.py` 표기는 오기).

**Goal**: 설명서 하나만 등록하면 기록 화면이 열리고 링크가 따라가며, 문서·문서 개정·계측기·검사원 자격이 새 화면으로 열린다
**Mode:** mvp
**Depends on**: Phase 4
**Requirements**: REC-01, REC-02, REC-03, REC-04, REC-07, REC-12, REC-13
**Success Criteria** (what must be TRUE):
  1. 문서·문서 개정·계측기·검사원 자격이 `/app/r/:app/:model/:id`에서 설명서만으로 그려진 기록 화면(제목·상태·칸·하위 표·오른쪽 열)으로 열리고, 설명서에 등록되지 않은 모델은 404다
  2. 사용자는 `records` API로 목록(탭·필터·엑셀)과 상세를 받고, 권한이 없는 사용자는 서버가 거부한다
  3. 검색·타임라인·종합현황·위젯·유사 건·메모·승인 후 돌아가기 링크가 모두 `record_url` 한 곳을 따라 옮긴 화면으로 열린다
  4. 옮긴 모델의 관리 화면 변경 페이지 위에 「새 화면으로」 링크가 있고, `/admin/` 주소와 권한은 그대로 열린다
  5. 모듈 대응표에 등록되지 않은 새 경로를 만들면 MOD-02 테스트가 실패한다

### Phase 6: 범용 저장과 승인·수정·삭제 요청 (B2)
> **착수 전 결정 (미결 #5)**: `submit_edit_request`를 `core/rules.py`로 옮길지. 동작은 바꾸지 않고 기존 테스트를 회귀망으로 쓰는 전제다. AGENTS.md상 요청받지 않은 리팩터링이라 사용자 승인이 먼저다. 거부하면 범용 API가 뷰의 수정 요청 로직을 복제해 규칙이 두 군데가 된다.

**Goal**: 사용자가 기록 화면에서 칸을 고치고 승인·요청을 낼 수 있고, 그 경로로 잠금·서명·검증이 약해지지 않는다
**Mode:** mvp
**Depends on**: Phase 5
**Requirements**: REC-05, REC-06
**Success Criteria** (what must be TRUE):
  1. 사용자가 기록 화면에서 「수정」으로 칸을 바꾸고 저장하면 모델 검증(`full_clean`)과 잠금을 거치고, 오류는 칸별로 보이며, 변경이 simple-history 이력에 남는다
  2. 사용자는 기록 화면에서 승인(비밀번호 재입력)·수정 요청·삭제 요청을 할 수 있다
  3. 승인된 기록은 화면에서도 서버에서도 수정되지 않는다
  4. 범용 저장으로 승인자·승인일·판정 같은 서명·승인 칸을 바꾸려 하면 거부되고, 그 값은 승인 서명 경로로만 바뀐다

**Mode:** mvp
**Depends on**: Phase 6
