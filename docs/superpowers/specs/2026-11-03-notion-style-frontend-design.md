# 업무 화면 재설계 — "데이터베이스 + 페이지" 방식 (설계)

- 작성: 2026-11-03
- 상위 문서: `docs/architecture-migration-plan.md`. 이 문서는 그 계획의 2·3단계 화면을 **어떤 모양과 동작으로** 만들지 정한다.
- 상태: 사용자 검토 대기

## 1. 왜 하는가

사용자는 품질관리자다. 현장과 여러 곳에서 품질 데이터를 받아 입력하고, 정리해서 내보낸다.

지금 화면(Django admin 기본 입력 화면, `/inspect/`)은 이 일에 맞지 않는다. 사용자가 짚은 문제는 다음과 같다.

- **데이터에 닿는 길이 길다.**
  - 검사 입력은 LOT 번호를 알고 있어야 시작된다. 번호를 치거나 스캔해야 한다.
  - 검사를 기다리는 LOT이 무엇인지 화면이 먼저 보여 주지 않는다.
- **기준·문서를 만들고 고치기 힘들다.**
  - 검사기준 화면은 짧은 값 네 개(품번·구분·개정·샘플링)를 한 줄에 하나씩 쌓는다.
  - 비고 칸이 지나치게 크고, 정작 중요한 검사항목 표는 맨 아래에 밀려 있다.
  - 개정은 목록 화면의 "동작" 메뉴에 숨어 있다.
  - 영어 문구가 남아 있다("Select an option").
- **깨끗한 데이터를 바로 내보내기 어렵다.**
  - 지금 보고 있는 목록을 그대로 엑셀로 받을 수 없다.

사용자가 바라는 것은 Notion처럼 쉬운 입력이다.

- 목록이 먼저 보인다.
- 누르면 바로 열린다.
- 칸을 누르면 바로 쓸 수 있다.
- 개정은 버튼 하나로 된다.

## 2. 목표 · 비목표 · 실패 조건

**목표**

1. **최단 경로:** 어느 화면에서든 두 동작 안에 원하는 기록을 연다.
   - 명령창(Ctrl+K)을 열고 번호 일부를 친 뒤 Enter를 누른다.
   - 또는 목록에서 한 줄을 누른다.
2. **빠르고 정확한 입력:** 하위 항목(검사항목 등)을 표 칸에서 바로 고친다.
   - 엑셀에서 복사한 여러 줄을 한 번에 붙여 넣을 수 있다.
   - 잘못된 값은 그 칸에 바로 표시한다.
3. **쉬운 개정:**
   - 승인된 기준에서 "새 개정" 버튼 하나로 다음 개정 초안을 만든다.
   - 이전 개정과 달라진 칸을 강조한다.
   - 승인 서명도 같은 화면에서 한다.
4. **깨끗한 내보내기:**
   - 지금 보이는 목록(필터·정렬 적용)을 엑셀로 받는다.
   - 기록 하나를 `.xlsx`·PDF 문서로 받아 그대로 증적으로 낸다(P6).
5. **뜻 있는 이력만:** 화면과 문서의 개정 이력에는 사용자가 신청하고 승인된 것만 나온다(P7).
6. **전면 개편:** 사이드바의 모든 메뉴를 새 화면으로 바꾼다(4장).

**비목표**

- Notion식 자유 블록 문서는 만들지 않는다. 아무 데나 글·표를 끼워 넣는 기능이다. 이 시스템은 구조화된 업무 데이터가 본질이다.
- 실시간 공동 편집은 하지 않는다.
- 업무 규칙은 바꾸지 않는다(`docs/business-rules.md`).
- 이번 설계로 기존 화면을 지우지 않는다. 지우는 시점은 상위 문서의 5단계다.

**실패 조건** (동작은 해도 실패로 본다)

- 보기엔 좋은데 승인 잠금, 판정 후 수정 불가 같은 규칙을 화면만 지킨다. 규칙은 서버(모델 `save`/`clean`, `core/rules.py`)가 지켜야 한다.
- 지금보다 클릭이나 입력 단계가 늘어난다.
- 새 의존성이 생긴다. npm과 Python 모두 지금 설치된 것만 쓴다.
- 자동 감사 기록(simple-history)이 사라지거나 줄어든다. 두 층 이력은 화면에서만 나눈다.

## 3. 화면 패턴 (모든 업무 화면이 이 일곱 가지를 함께 쓴다)

### P1. 앱 틀 + 명령창

- **왼쪽 사이드바:** 접을 수 있다.
  - 맨 위에 "최근 연 기록" 5개와 "즐겨찾기"가 있다.
  - 그 아래에 모듈 묶음(기준정보·생산·품질·고객·분석)이 있다.
- **Ctrl+K 명령창:**
  - 화면 어디서나 연다. LOT·품번·부적합·CAPA·8D·SCAR 번호를 친다.
  - "새 부적합", "검사 시작" 같은 동작도 여기서 바로 실행한다.
  - 서버는 기존 `core.search.search(user, q)`를 API로 감싼다. 권한 거르기도 이 함수가 이미 한다.
- **최근 기록과 즐겨찾기의 저장 위치:**
  - 최근 기록은 브라우저 `localStorage`에 둔다. 사용자 편의 기능이라 서버에 두지 않는다.
  - 즐겨찾기는 서버에 둔다. 다른 PC에서도 보여야 하기 때문이다.
  - 서버 저장은 기존 `DashboardLayout` 처리 방식을 따른다. 이것은 **내 판단**이다. 1차에는 "최근"만 만든다.

### P2. 데이터 목록 (Notion의 데이터베이스 보기)

- 한 화면에 한 표를 둔다. 표 위에 다음이 있다.
  - **보기 탭:** 예를 들어 "전체 / 승인 대기 / 내가 만든 것". 화면마다 미리 정한 탭이다.
  - **필터 칩, 검색칸, 열 정렬**
  - **"엑셀로" 버튼**
- **줄을 누르면 오른쪽 미리보기 패널이 열린다.** 페이지는 바뀌지 않는다.
  - 패널에서 바로 고칠 수 있다.
  - "전체 화면으로"를 누르면 P3 페이지로 간다.
- **페이지 나눔:** 서버가 한 번에 50줄씩 준다. 표 아래에 "더 보기"가 있다.
- **엑셀 내보내기:**
  - 서버가 openpyxl로 만든다.
  - 지금 필터·정렬을 그대로 쓰고 모든 줄을 담는다. 화면에 불러온 줄만이 아니다.
  - 열은 화면 표와 같다.

### P3. 기록 페이지 (Notion의 페이지)

- **맨 위:** 제목(예: `D-RM-AL 수입검사 Rev.2`)과 상태 배지(초안 / 승인됨 / 잠김)가 있다.
- **속성 블록:** 짧은 값을 두 열의 "이름 : 값" 줄로 촘촘히 보인다. 값을 누르면 그 자리에서 고친다.
- **본문:** 하위 항목 표가 있다(P4).
- **긴 글(비고 등):** 필요할 때만 펼쳐지는 글 칸으로 둔다.
- **오른쪽 탭:** "개정 이력"(P7의 신청된 이력만)과 "메모". 자동 기록(simple-history)은 "감사 기록" 메뉴에서만 본다.
- **저장 방식 (내 판단):** 자동 저장은 하지 않는다.
  - 고친 것이 있으면 아래쪽에 "변경 N건 · 저장(Ctrl+S) · 취소" 띠가 나타난다.
  - 이유 1: 칸마다 자동 저장하면 변경 이력이 칸 수만큼 쌓인다.
  - 이유 2: 승인 잠금·수정 요청 흐름과도 어긋난다.
  - 저장은 한 번의 요청이다. 속성과 하위 항목을 같은 트랜잭션에 담는다(`core.rules.save_with_lock`).

### P4. 편집 표 (하위 항목 격자)

- 칸을 누르면 바로 입력한다.
  - Tab으로 오른쪽 칸, Enter로 아래 칸으로 간다.
  - 맨 아래 빈 줄에 쓰면 새 줄이 생긴다.
- **엑셀 붙여넣기:**
  - 탭으로 나뉜 여러 줄을 붙여 넣으면 누른 칸부터 채운다. 모자라는 줄은 새로 만든다.
  - 클립보드 글을 직접 나눈다. 라이브러리를 쓰지 않는다.
- **줄 삭제:** 줄 끝의 휴지통 버튼. 저장 전까지는 취소선으로만 보인다.
- **고르는 칸(특별특성, 관리계획서 항목 등):**
  - 한국어 선택 목록을 쓰고 글자를 쳐서 찾을 수 있다.
  - "Select an option" 같은 영어 문구는 남기지 않는다.
- **서버 오류 표시:**
  - 오류는 해당 줄·칸 옆에 표시한다.
  - 지금 `frontend/src/api/client.ts`는 DRF 필드 오류를 칸별로 풀지 못한다. 이번에 함께 고친다.

### P5. 승인 · 개정 · 잠금

- **승인된 기록:** 모든 칸이 읽기 전용으로 보이고 잠금 표시가 붙는다. 서버 쪽 막기는 이미 모델에 있다.
- **"새 개정" 버튼:**
  - 다음 개정 초안을 만들고 그 페이지로 간다.
  - 서버 로직은 admin 동작 `InspectionSpecAdmin.new_revision`의 본문을 공용 함수로 옮긴다.
  - admin과 API가 같은 함수를 부르고, 동등성 테스트로 확인한다. 상위 문서 3.2와 같은 방식이다.
- **초안 페이지:** "이전 개정과 비교"를 켜면 바뀐 칸은 배경색으로, 추가·삭제된 줄은 표시로 보인다.
- **"승인 서명" 버튼:** 비밀번호 입력 창을 띄운다. 서버는 `core.rules.approve`를 쓴다.
- **잠긴 기록의 "수정 요청" 버튼:** 기존 `EditRequest` 흐름을 API로 부른다.

### P6. 문서 내보내기 (.xlsx · PDF)

웹에서 작성한 기록을 그대로 문서나 증적 자료로 받는다.

- **출력 버튼 위치:** 각 기록 페이지(P3) 머리 버튼 줄의 "내보내기 ▾ (.xlsx · PDF)"에 둔다. 따로 "문서 출력" 메뉴나 전역 버튼은 만들지 않는다(사용자 결정). PDF를 고르면 그 기록의 A4 인쇄 화면이 열리고, 거기서 인쇄 창 또는 `.xlsx` 받기를 누른다.

- **한 구조, 두 출력:**
  - 서버가 기록마다 "문서 구조"를 만든다. 내용은 다음과 같다.
    - 제목·문서번호·개정
    - 머리 정보 칸
    - 본문 표 여러 개
    - 개정 이력 표(P7)
    - 승인란(작성·승인·일자)
  - 이 구조를 두 가지로 낸다.
    - `.xlsx`: openpyxl로 A4 인쇄 설정까지 넣어 만든다.
    - PDF: React 인쇄 화면이 같은 구조를 A4로 그리고, 사용자가 인쇄 창에서 "PDF로 저장"을 누른다. 사용자 결정이며 새 의존성은 없다.
  - 기존 `print_table()`(머리 정보 + 표)을 이 구조로 넓힌다. 기존 인쇄 화면도 같은 구조를 쓰게 되어 내용이 어긋나지 않는다.
- **회사·고객 양식:** 기존 `ExcelTemplate`(셀 매핑) 양식이 있으면 그 양식으로 채운다.
  - 지금 매핑은 칸 하나에 값 하나라 검사항목처럼 여러 줄인 표를 못 채운다.
  - 그래서 "이 행부터 하위 항목을 한 줄씩 채움" 매핑을 더한다. 예: `{"A12:rows": "characteristics", "A": "name", "B": "lsl"}`
- **"초안" 표시:** 승인 전 기록을 내보내면 모든 쪽에 "초안 — 승인 전" 표시가 붙는다. 승인 전 문서가 증적으로 잘못 쓰이지 않게 하려는 것이다.
- **대상:** 다음 기록에 문서 출력이 있다.
  - 검사기준서, 관리계획서, 검사 성적서
  - 부적합 보고서, CAPA, 8D, SCAR, 4M 변경
  - 내부심사 보고서, PPAP 제출, 문서 개정
  - 각 묶음을 만들 때 그 기록의 문서 구조를 같이 만든다.

### P7. 변경 이력 — 두 층 (사용자 결정 2026-11-03)

- **감사 기록 (기존 그대로):**
  - 저장할 때마다 시스템이 자동으로 남기는 simple-history는 지금처럼 유지한다. 핵심 보호 규칙이다.
  - 업무 화면에는 보이지 않는다. "기준정보 및 시스템 관리 › 감사 기록"에서만 조회하고, 조회 권한은 품질팀장과 관리자다.
- **개정 이력 (새로 만든다):**
  - 사용자가 "이력 남기기"를 신청할 때만 한 줄 생긴다. 화면의 개정 이력 탭과 내보낸 문서의 개정 이력 표에는 이것만 나온다.
  - 한 줄의 내용: 대상 기록, 개정 표시(예: Rev.2), 변경 내용, 사유, 신청자·신청일, 승인자·승인일
  - **흐름:**
    1. 사용자가 "이력 남기기"를 누른다.
    2. 변경 내용 칸이 미리 채워진다. 마지막 개정 이력 이후 감사 기록에서 바뀐 칸 목록이다. 사용자가 이를 다듬고 사유를 쓴다.
    3. 신청하면 상태는 "대기"다.
    4. 승인자(`is_approver`)가 비밀번호를 다시 입력해 서명하면 "확정"된다. 기존 승인 서명과 같은 방식이다.
  - 승인 서명이 있는 기록(검사기준·관리계획서·문서 개정·4M·PPAP)은 승인 서명과 이력 확정을 한 번에 할 수 있다. "승인하며 이력 남기기"다.
  - 확정된 개정 이력은 고치거나 지울 수 없다. 기존 잠금 규칙처럼 모델 `save()`가 막는다.
- **모델 (내 판단):**
  - `core`에 `RevisionLog` 하나를 둔다. 대상 기록은 `ContentType` + `object_id`로 가리킨다(일반 연결).
  - 이 모델 자체도 `history = HistoricalRecords()`를 둔다.
  - 새 테이블만 추가하므로 기존 행은 바뀌지 않는다. 운영 DB에 적용하기 전 `backup`은 규칙대로 한다.

## 4. 전면 개편 범위 — 사이드바 모든 메뉴

admin 기본 화면과 기존 템플릿 화면을 모두 새 화면으로 바꾼다. 묶음별 대상과 쓰는 패턴은 아래와 같다.

| 묶음 | 메뉴 | 화면 모양 |
| --- | --- | --- |
| 통합 업무 홈 | 내 할 일, 공장 종합현황 | 이미 React 시범 화면. 새 틀(P1)에 맞춰 다듬는다 |
| | 미분류 메모 | 목록(P2) + 미리보기 패널 |
| | 연차·급여 | 본인 전용 페이지(P3). 본인만 열람하는 규칙을 서버가 그대로 지킨다 |
| 생산관리 (MES) | 작업지시, 작업 실적, LOT, 출하 | 목록(P2) + 기록 페이지(P3) |
| | LOT 이력 조회 | 계보 트리 + 시간순 타임라인(`core.timeline` 재사용) |
| 품질관리 (QMS) | 검사 입력 | 5.2 화면 |
| | 수입·공정·출하검사 | 한 목록의 보기 탭 3개. 성적서 문서 출력(P6) |
| | 계측기·교정 | 목록 + 교정 기한 색 표시 |
| | 검사원 자격 | 목록 + 유효기한 색 표시 |

## 5. 첫 화면 두 개

### 5.1 검사기준서 (`/app/specs`, `/app/specs/:id`)

- **목록:**
  - 열: 품번, 품명, 검사 구분, 개정, 상태, 항목 수, 승인자·승인일
  - 보기 탭: 전체 / 초안 / 승인됨 / 유효본만(품번·구분별 승인된 최신 개정)
- **페이지:**
  - 속성: 품번(검색 선택), 검사 구분, 개정(읽기 전용, 서버가 정함), 샘플링, 비고
  - 본문: 검사항목 편집 표. 열은 항목명, 하한, 상한, 단위, 특별특성, 관리계획서 항목, SPC 관리도 링크다.
- **새 기준서:**
  - 품번과 검사 구분만 고르면 Rev.1 초안이 만들어진다.
  - 같은 품번·구분이 이미 있으면 "새 개정"으로 안내한다.
- **규칙 (모두 서버에 이미 있음):**
  - 승인된 기준의 항목은 수정할 수 없다(`Characteristic.save`).
  - 품번·구분·개정 조합은 하나만 있다(`uniq_spec_rev`).
  - 검사는 승인된 최신 개정만 쓴다(`Inspection.clean`).

### 5.2 검사 입력 (`/app/inspect`)

- **맨 위:** LOT 스캔 칸을 유지한다. 바코드 스캐너는 키보드 입력 + Enter로 동작한다.
- **그 아래 "검사 대기" 목록 (기본 화면):**
  - 대상은 검사가 아직 없고, 그 품번·구분에 승인된 현재 기준이 있는 LOT이다(`InspectionSpec.current`).
  - 보기 탭: 수입 / 공정 / 출하
  - 열: LOT, 품번, 협력사, 수량, 생성일, 보류 여부
  - 오래된 순으로 보인다.
  - 이 정의는 **내 판단**이다. 기간 제한(예: 최근 90일)이 필요한지는 데이터가 쌓인 뒤 정한다.
- **줄을 누르면 측정 화면이 열린다:**
  - 항목마다 규격과 입력칸이 있다. 입력하는 즉시 합격·규격 이탈 색이 보인다. 판정은 서버 `measurement()`가 한다.
  - 계측기는 사용 가능한 것만 고를 수 있다(`Gauge.usable_on`).
  - "판정" 버튼을 누르면 서버 `submit_inspection()`이 처리한다. 불합격이면 부적합 번호가 보인다.
- **처음 들어온 자재:**
  - 스캔한 LOT이 없으면 그 자리에서 입고 등록 창을 띄운다.
  - 서버는 기존 `receive_lot()`를 쓴다.

## 6. 서버 쪽 (상위 문서 6장 방식을 따른다)

- **API 위치:** 화면마다 `qms/api/`(검사기준·검사)에 둔다. 저장은 반드시 `core.rules.save_with_lock` 등 공용 함수를 거친다.
- **새로 만드는 엔드포인트:**
  - 검색: `GET /api/search/?q=`
  - 검사기준 목록·상세·저장
  - 개정·승인: `POST …/new-revision/`, `POST …/approve/`
  - 개정 이력: `GET/POST …/revision-log/`, `POST /api/revision-log/:id/approve/`
  - 감사 기록: `GET /api/audit-log/?model=&id=` (품질팀장·관리자만)
  - 문서 구조: `GET …/document/`. 같은 구조로 `GET …/document/?format=xlsx`
  - 목록 엑셀: `GET …?format=xlsx`
  - 검사 대기 목록
  - 측정 확인
  - 판정
- **권한:** 기존 Django 권한(`ensure_roles`)을 그대로 쓴다. 화면에서 버튼을 숨기는 것은 편의일 뿐이다.

## 8. 순서 (단계마다 따로 구현 계획을 쓴다)

1. **공통 틀 + 검사기준서:**
   - P1~P7 공통 부품. 문서 구조, 개정 이력 모델, 감사 기록 화면을 포함한다.
   - 5.1 화면과 검사기준서 문서 출력(.xlsx·PDF)
   - 필드 오류 표시 개선
   - ← 첫 구현 계획
2. **검사 입력:** 5.2 화면 + 수입·공정·출하검사 목록 + 검사 성적서 출력
3. **기준정보 나머지:** 품번·BOM·라우팅·공정·관리계획서·고객사별 8D 기한·엑셀 일괄 등록
4. **품질관리 나머지:** 계측기·교정, 검사원 자격
5. **품질보증 및 개선:** 부적합·보류·CAPA·4M·문서·내부심사·심사 체크리스트·심사 자료 출력
6. **생산관리:** 작업지시·작업 실적·LOT·LOT 이력 조회·출하
7. **고객 및 협력사:** 8D·SCAR·PPAP·협력사 평가
8. **분석·홈:** 품질 KPI·엑셀 보고서 양식·내 할 일·종합현황·메모·연차·급여

- 묶음마다 다음을 함께 끝낸다.
  - 그 묶음 기록의 문서 출력(P6)
  - 동등성 테스트
  - Playwright 흐름 점검
- 모든 묶음이 끝나면 상위 문서 5단계(일괄 교체)로 간다.

## 9. 완료 기준 (1번 묶음)

- 검사항목 10줄을 엑셀에서 복사해 한 번에 붙여 넣고 저장하면, 서버에 10개 항목이 생긴다.
  - Playwright 점검을 추가하고, 화면 폭은 PC 기준이다.
- 승인된 기준에서 "새 개정"을 누르면, 항목이 복사된 Rev+1 초안 페이지가 열린다.
  - 같은 요청을 admin 동작으로 했을 때와 결과가 같다(동등성 테스트).
- 승인된 기준의 항목을 API로 바꾸려 하면 거부된다(API 테스트).
- Ctrl+K에서 LOT 번호 일부를 치고 Enter를 누르면 그 기록이 열린다.
- **문서 출력:** 승인된 검사기준서를 `.xlsx`로 받으면 한 시트에 다음이 모두 들어 있다(테스트로 셀 확인).
  - 머리 정보·검사항목 표·개정 이력 표·승인란
  - A4 인쇄 설정
- **PDF:** 같은 기준서의 인쇄 화면을 PDF로 저장하면 A4 한 장 배치를 유지한다(Playwright `page.pdf`로 쪽 수 확인).
- **초안 표시:** 승인 전 기준서의 출력물에는 "초안 — 승인 전" 표시가 있다.
- **개정 이력 확정:** "이력 남기기" 신청 → 승인 서명 → 확정된 줄은 다시 바꾸면 거부된다(모델 테스트).
- **개정 이력 표시:** 신청하지 않은 저장은 개정 이력 탭에 나오지 않는다. 감사 기록(simple-history)에는 그대로 남는다(테스트로 둘 다 확인).
- 기존 검증이 모두 통과한다: `manage.py test`, `e2e_check.py`, `e2e_browser.py`

## 10. 검토 질문에 대한 답 (코드 확인 또는 내 판단)

1. **하위 항목 줄 삭제** (코드 확인):
   - 초안 기준서의 검사항목 줄 삭제는 지금 admin과 같게 한다.
     - 근거: `CharacteristicInline`(`LockedWhenApprovedInline`)은 승인 전에는 `delete_characteristic` 권한만 있으면 줄을 지울 수 있다.
     - "삭제는 시스템 관리자만"은 기록 자체(검사기준)의 삭제 규칙이다(`BaseAdmin.has_delete_permission`). 규칙 완화가 아니다.
   - 저장 요청은 하위 항목 전체를 담는다(추가·변경·삭제 표시).
     - 서버는 한 트랜잭션에서 처리한다.
     - 이 처리를 `save_with_lock`을 감싸는 공용 함수로 만든다.
     - 이력은 지금처럼 줄(모델)마다 simple-history에 남는다.
2. **이미 초안이 있을 때 "새 개정"** (내 판단):
   - 같은 품번·구분에 미승인 개정이 있으면 새로 만들지 않고 그 초안을 연다.
     - admin 동작은 이 경우에도 개정을 하나 더 만든다. 그래서 이 점만 admin과 다르다.
     - 동등성 테스트는 "초안이 없을 때 복사 결과(항목·샘플링·비고·관리계획서 연결)가 같다"로 한정한다.
   - 복사 범위는 `new_revision` 본문 그대로다. SPC 관리도는 항목 이름으로 이어지므로 따로 복사할 것이 없다.
3. **"유효본"과 "검사 대기"** (코드 확인):
   - 유효본은 `InspectionSpec.current` = 승인된 것 중 개정번호가 가장 큰 것이다. 그보다 높은 초안이 있어도 유효본은 승인본이다.
   - "검사 대기"는 그 LOT에 해당 구분의 검사 기록이 하나도 없는 경우다. 판정 전 검사(`result=''`)도 "있음"으로 본다.
4. **즐겨찾기** (확정): 1번 묶음에서 뺀다. 1번 묶음에는 브라우저에 두는 "최근"만 만든다. 모델·마이그레이션은 없다.
5. **동시에 고친 경우** (내 판단):
   - 페이지를 열 때 받은 마지막 이력 번호(`history.latest().history_id`)를 저장 요청에 함께 보낸다.
   - 서버의 최신 이력 번호와 다르면 409로 거부한다. 화면은 "다른 사람이 먼저 고쳤습니다. 다시 불러오세요"를 보인다.
   - 스키마 변경은 없다.
6. **붙여넣은 줄 중 일부가 틀린 경우** (내 판단):
   - 전부 저장하지 않는다(한 트랜잭션).
   - 서버는 줄 번호별·칸별 오류를 돌려준다. 화면은 해당 칸을 빨갛게 표시한다.
7. **권한** (내 판단, 새 권한 없음):

   | 동작 | 필요한 권한 |
   | --- | --- |
   | 조회·엑셀 내보내기 | `view_inspectionspec` (admin 목록에서 이미 보는 데이터와 같다) |
   | 새로 만들기·새 개정 | `add_inspectionspec` |
   | 수정 | `change_inspectionspec` + `change_characteristic` 등 하위 권한 |
   | 승인 | `is_approver` |
   | 명령창 | `core.search.search`의 기존 권한 거르기 |

8. **기반 상태** (코드 확인):
   - 0·1단계는 끝났다(커밋 `fcfd2a9`~`94dabde`). 세션 인증, CSRF, `/app/` 라우팅(`basename="/app"`), `client.ts`가 있다.
