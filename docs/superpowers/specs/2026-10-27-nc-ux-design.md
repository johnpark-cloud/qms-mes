## 1. 왜 하는가

사용자(품질 엔지니어)가 실제로 써 보고 느낀 불편 세 가지에서 출발했다.

1. 잘못 입력한 기록을 지우려면 목록에서 체크 → "작업" 드롭다운 → 삭제를 찾아야 한다. 삭제 버튼이 눈에 보이지 않는다.
2. 입력 화면이 복잡하다. 예: CAPA의 "출처 기록 종류" 드롭다운에 Django 내부 모델이 전부 나온다.
3. 부적합 기록이 너무 단순하다(LOT·내용·불량유형·수량·비용·처분뿐). 내부 공정/협력사 구분도 없고 사진도 못 붙인다. 사용자는 예전 양식이 기억나지 않으므로 **IATF 16949가 요구하는 수준을 빠짐없이 담은 기본 양식**을 원한다.

**기본 원칙(사용자 지정): "최소 인원으로 운용하는 QMS+MES, 그러나 고객사·심사원 앞에서 부족함이 없을 것."**

- 필수 데이터만 관리한다. 입력은 줄이고 자동으로 채울 수 있는 것은 채운다.
- 맥락 기반 UI: 지금 상태에서 필요한 칸과 버튼만 보인다.
- 메뉴 탐색 단계를 최소화한다. 통합형 인터페이스.
- 증적(이력·사진·승인 서명)은 자동으로 남고, 요청 시 바로 출력할 수 있다.

## 5. 설계

### 5.1 삭제·수정 요청과 관리자 승인 (G1, G10)

**흐름**
1. 일반 사용자: 목록 각 행 끝과 상세 화면 상단에 "삭제 요청" 버튼(승인된 기록이면 "수정 요청"도). 누르면 사유(필수) + **본인 암호** 입력 화면.
2. 암호가 맞으면 `ChangeRequest`와 이름이 겹치지 않는 새 모델 `EditRequest`(요청 종류: 삭제/수정, 대상 GFK, 사유, 요청자, 요청 시각, 상태: 대기/승인/거절, 처리자, 처리 시각, 거절 사유)가 생긴다. 원본은 그대로.
3. 시스템 관리자의 "내 할 일"에 "삭제·수정 요청 대기"로 뜬다. 관리자는 대상 기록을 보고 승인/거절.
   - 삭제 승인: 그 자리에서 삭제 실행(아래 규칙 적용).
   - 수정 승인: 그 기록의 잠금을 **1회 수정 동안** 풀어 준다. 요청자가 저장하면 다시 잠긴다.
   - 거절: 사유가 요청자의 "내 할 일"에 남는다.
4. 시스템 관리자 본인은 요청 없이 바로 삭제·수정 가능(모든 권한). 이력은 똑같이 남는다.

**수정 요청이 필요한 대상** (내 판단): 승인 서명이 끝난 기록과 "이전 방식 승인"된 부적합만. 승인 전 기록은 지금처럼 바로 수정한다. 모든 수정에 관리자 승인을 받으면 관리자 한 명이 병목이 되기 때문이다. 삭제는 기록 종류와 상관없이 항상 요청이 필요하다.

**삭제 실행 규칙**
- 다른 기록이 PROTECT로 참조하면 승인해도 지울 수 없다. 승인 화면에서 "먼저 지워야 할 기록"을 안내한다(Django 삭제 확인 화면의 연관 목록 재사용).
- 부적합 삭제: 그 부적합의 `Hold`를 먼저 지우고 첨부 사진 파일도 지운다. 한 트랜잭션.
- 이력: simple_history의 삭제 이력 + `EditRequest` 기록(누가·왜·누가 승인) 둘 다 남는다.
- Django 기본 "선택 항목 삭제" 일괄 작업은 일반 사용자에게서 뺀다.

**시스템 관리자**: `is_superuser`. 관리 화면의 모든 메뉴·기록 접근(Django 기본). 로그인은 필요. 승인 서명(`core.views.approve`)은 관리자도 암호 입력 유지.

### 5.2 입력 화면 단순화 (G2)

- CAPA "출처 기록 종류": `limit_choices_to`로 고객 클레임(8D), SCAR, 부적합, 심사 지적 4개만. 출처 화면의 "CAPA 만들기" 링크로 들어오면 이미 채워져 있으므로 대부분 손댈 일이 없다.
- 관리 화면 입력 폼 공통 규칙: 필수 칸만 위에, 나머지는 "추가 정보" 접힘 영역(fieldsets `collapse`)으로.
- 구체적인 모델별 정리 범위(어느 칸을 접을지)는 빌더가 정한다. 기준: 등록 시점에 보통 모르는 값·자동 계산 값·드물게 쓰는 값은 접는다.

### 5.3 부적합 보고서 (G3) — IATF 16949 8.7.1, 8.7.2, 10.2.1 기준

기존 `core.Nonconformance`를 확장한다(새 모델로 갈아타지 않음 — 기존 인터록·KPI·8D 연결 유지).

| 구역 | 칸 | 비고 |
| --- | --- | --- |
| ① 구분 | **발생 유형**(필수): 수입검사·협력사 / 공정 내부 / 출하검사 / 고객 클레임 / 반품 | 이 값으로 아래 칸 표시가 바뀐다 |
| | 발견 공정(Process FK, 선택), 발견자(user, 기본=입력자), 발견 일시(기존) | |
| ② 대상 | LOT(기존, 필수), 품번·협력사(LOT에서 자동 표시, 입력 아님), 불량 수량(기존), 검사·로트 수량 | 협력사 칸은 수입검사 유형에서만 표시 |
| ③ 현상 | 불량 유형(기존), 상세 내용(기존 description, 5W1H 안내문), 규격 대비 측정값(텍스트), **사진 여러 장**, 특별특성(CC/SC) 해당 여부 | |
| ④ 긴급 조치 | 격리 수량, 재고·재공·출하분 선별 결과, 고객 통보 필요 여부(+통보일) | 고객 통보 필요인데 통보일 없으면 "내 할 일"에 표시 |
| ⑤ 처분 | 처분(기존 5종), 특채 고객 승인번호(기존), 실패비용(기존) | 기존 규칙 그대로 |
| ⑥ 후속 | 시정조치 필요 여부 → 필요 시 CAPA 만들기 링크(기존 `capa_links`), 협력사 유형이면 SCAR 링크, 고객 클레임이면 8D 링크 | 링크로 연결, 자동 생성 안 함 |
| ⑦ 승인 | 내부 승인(MRB): **비밀번호 재확인 승인**으로 바꾼다 | 아래 참고 |

- 사진: 별도 모델 `NonconformancePhoto(nonconformance FK, file, caption, uploaded_at)`. 인라인으로 여러 장. 확장자 jpg/jpeg/png/heic/webp만, 장당 크기 상한(빌더 결정, 10MB 권장).
- 번호: 지금 `NC-{pk}`. 보고서·메일에 쓰기 위해 `NC-YYMMDD-NNN` 형식 번호 칸을 추가한다(CAPA 번호와 같은 방식). 기존 행은 마이그레이션에서 채운다.
- **내부 승인 변경**: 현재는 관리 화면에서 "MRB 승인자"를 드롭다운으로 고른다(본인 확인 없음). 이것을 기존 `core.views.approve`(비밀번호 재확인) 흐름으로 바꾸고 `approved_at`을 추가한다. 처분 규칙("처분에는 MRB 승인자 필요")은 그대로 유지하되 승인자는 승인 화면으로만 채워진다.
  - 승인 순서: 처분 입력 → 승인 서명 → (보류 해제·종결). 승인 전 처분 저장 시 보류 해제가 일어나지 않아야 한다. 정확한 순서 처리는 빌더가 기존 `clean`/`save` 규칙과 맞춰 정한다.
- 출력: 부적합 보고서 인쇄 화면(①~⑦ + 사진 썸네일 + 승인 서명). 기존 print 화면 패턴. 고객사·심사원 제출용.

### 5.4 간편 등록 후 보완 (G4)

- 화면: `/nc/new/` (관리 화면 밖, 검사 입력 화면처럼 큰 버튼·큰 글씨, htmx).
- 입력 3가지 + LOT: **LOT(스캔/검색), 발생 유형, 현상(한 줄), 불량 수량, 사진**. 나머지는 자동(발견자=로그인 사용자, 일시=지금, 품번·협력사=LOT).
- 저장 즉시 기존 인터록 작동(LOT + 하위 보류).
- "보완 필요" 판정: ③④의 필수급 칸(상세 내용·긴급 조치 등, 빌더가 목록 확정)이 비어 있으면 "내 할 일"에 "부적합 보완 필요"로 뜬다. 승인은 보완이 끝나야 가능.
- 검사 입력 화면(/inspect/)에서 불합격 시 자동 생성되는 부적합도 같은 "보완 필요" 흐름을 탄다.

### 5.5 카메라 촬영 (G5)

- 모든 사진 입력칸에 `accept="image/*" capture="environment"`. PC에서는 파일 선택, 휴대폰에서는 카메라가 열린다.
- 휴대폰 접속(사내 Wi-Fi에서 PC 서버 접속)은 **기본 꺼짐**. README에 켜는 방법을 쓴다: `QMS_ALLOWED_HOSTS`에 PC IP 추가, 서버를 `0.0.0.0`으로 실행, Windows 방화벽 인바운드 허용. 회사 보안 정책 확인이 선행 조건임을 명시.

### 5.6 메일 보내기 (G6)

- 조건: 부적합 승인 완료 후에만 버튼 표시.
- **"메일 내용 복사"** 버튼(기본):
  1. 제목 한 줄 + 보고서 요약 표(HTML)를 클립보드에 복사 (`navigator.clipboard.write`, text/html + text/plain 둘 다). localhost는 보안 컨텍스트라 동작.
  2. 사진 전체 ZIP 받기(stdlib `zipfile`), 보고서 인쇄 화면 열기(→ PDF 저장).
  3. 사용자가 아마란스 웹메일 작성창에 붙여넣고 파일 첨부.
- **"바로 보내기"** 버튼: `QMS_SMTP_HOST`가 설정된 경우에만 표시. 수신자 입력칸 + 기존 `MAILERS` 설정으로 발송, 사진 첨부.
- 발송/복사 기록: 부적합에 `mailed_at`(마지막 발송·복사 시각)을 남긴다. 승인됐는데 `mailed_at` 없으면 "내 할 일"에 "메일 발송 대기".
  - 복사는 실제 발송 여부를 알 수 없으므로, 복사 후 "보냈음" 확인 버튼으로 `mailed_at`을 찍는다. (내 판단)
- 수신자 기본값: 부적합 유형별 기본 수신자 목록이 필요할 수 있음 → §8 열린 질문.

### 5.7 통합 검색창 (G7)

### 5.11 로고·CI 디자인·사이드바 (G11)

- **로고**: 셸바 왼쪽. 파일은 회사 데이터 폴더 `data/brand/logo.(png|jpg|svg)`(이식 원칙: 회사 자산은 저장소에 넣지 않음). 없으면 지금처럼 "QMS+MES" 글자. 로고 원본은 흰 배경 JPG이므로 흰 셸바 위에 둔다(`mix-blend-mode: multiply`로 흰 배경 제거 효과).
- **색**: 기존 `fiori.css`의 브랜드 토큰(`--f-brand` 등, 지금 `#0070f2`)을 CI 남색 `#2C4D80`으로 교체. 같은 계열로 연한 배경(선택·호버), 진한 색(눌림), 다크 모드용 밝은 남색을 만든다. **텍스트 대비 WCAG AA(4.5:1) 이상**을 라이트·다크 모두에서 지킨다. 상태색(정상·주의·이상)은 의미 유지.
- **레이아웃 (A안, 사용자 선택)**:
  - 위: 흰 셸바 = 로고 + 통합 검색창(§5.7) + 사용자 메뉴, 아래쪽에 남색 3px 선.
  - 왼쪽: **남색 사이드바**, 그룹 MES(LOT 이력, 작업 실적…) / QMS(부적합, 검사 입력, CAPA·심사, KPI…) / 개인(연차·급여). 현재 위치는 흰 왼쪽 막대 + 밝은 배경으로 표시. "전체 메뉴"(관리 화면 인덱스)는 사이드바 맨 아래.
  - 좁은 화면(태블릿·휴대폰): 사이드바는 햄버거 버튼으로 접힌다.
  - 관리 화면 기본 사이드바(Django `nav-sidebar`)는 이 사이드바로 대체한다.
- **화면 상태 표시** 공통 템플릿: 빈 데이터("아직 기록이 없습니다" + 등록 버튼), 오류, 권한 부족(무엇이 없는지), 저장 성공. 기존 Django 메시지 프레임워크 재사용.
- 시안: `.superpowers/brainstorm/…/content/ci-style.html`(A안).

### 5.12 현장 메모 (G12)

심사원·감독관·고객의 말을 그 자리에서 관련 기록에 남겨, 나중에 기억으로 맞추는 수고를 없앤다.

- 모델 `Memo`: 본문, 말한 사람 구분(심사원/감독관/고객/내부/기타) + 이름(선택), 사진 여러 장(선택, §5.5 카메라 촬영 동일), 대상 기록(GFK, 비어 있으면 "미분류"), 심사(InternalAudit FK, 선택), 작성자·시각(자동).
- **입력 위치**:
  - 모든 기록 상세 화면(관리 화면 + 타임라인 + 부적합 화면)에 "메모" 버튼 → 작은 입력창(htmx). 대상 기록 자동 연결.
  - 통합 검색창에서 "메모" → 대상 없이 저장(미분류). 나중에 "미분류 메모"에서 검색으로 대상 연결.
- **심사 자동 묶기**: 실시일(`conducted_on` 등)이 오늘인 내부심사가 있으면 메모 입력창에 그 심사가 기본 선택돼 있다(해제 가능). 고객 심사도 같은 방식으로 쓰도록 InternalAudit에 "구분: 내부/고객/인증" 칸 추가. (내 판단)
- **모아 보기**: 심사 화면에 "이번 심사 메모" 목록(대상 기록별 묶음). 각 메모에서 "CAPA 만들기"(기존 링크 재사용, 출처=심사).
- 기록 상세 화면에는 붙은 메모가 시간순으로 보인다.
- 메모는 작성자 본인이 수정 가능, 삭제는 §5.1 요청 흐름.

### 5.13 개인 ERP: 연차·급여 (G13)

- 새 앱 `personal`(회사 업무 앱과 분리 — 다른 회사로 옮길 때 이 앱 데이터만 따로 내보내고 지울 수 있게).
- **본인만 열람**: 모든 기록에 `owner`(user). 화면·관리 화면 쿼리를 `owner=request.user`로 고정 — **시스템 관리자도 남의 기록은 보이지 않는다.** 백업 파일에는 포함됨(DB 전체 백업이므로) → README에 명시.
- **연차**:
  - 설정: 입사일.
  - 발생 일수 자동 계산(근로기준법 제60조): 1년 미만 1개월 개근마다 1일(최대 11일), 1년 이상 15일, 3년차부터 2년마다 1일 가산, 최대 25일. 회계연도 기준이 아닌 **입사일 기준**. (내 판단 — 회사가 회계연도 기준이면 바꿔야 함)
  - 사용 등록: 날짜, 일수(1, 0.5, 0.25), 사유. 잔여 = 발생 − 사용.
  - 계산 함수에 단위 테스트(경계: 입사 11개월, 1년, 3년, 21년 이상).
- **급여**:
  - 월별: 지급월, 기본급, 수당(항목 여러 개), 공제(항목 여러 개), 실수령액(= 지급 합계 − 공제 합계, 자동), 명세서 파일 첨부.
  - 연간 합계 표.
  - 세금·4대보험 자동 계산 없음(입력값 기록만).

### 5.14 위젯 대시보드 (G14, 사용자 추가 요청)

- 위치: 첫 화면 "내 할 일"(`/todo/`)을 위젯 격자로 바꾼다. 별도 화면을 만들지 않는다.
- **위젯 = 기존 계산 재사용.** 새 계산을 만들지 않는다. 계산은 `qms/due.py`, `qms/kpi.py`, 개인 앱에서 가져온다.
  - 숫자 타일: 보류 LOT, 부적합 보완 필요, 승인 대기, 메일 발송 대기, 삭제·수정 요청(관리자), 미분류 메모, CAPA 지연, 교정 임박.
  - 목록 카드: 기존 할 일 목록 각 묶음, 최근 SPC 경보, 14일 내 예정 심사.
  - KPI 카드: 고객 PPM, 초도 합격률, 공정 수율(기존 `/kpi/` 계산 요약).
  - 개인: 연차 잔여(본인만).
  - 권한이 없는 위젯은 목록에 나오지 않는다.
- **편집 모드**: "대시보드 편집" 버튼을 누르면 편집 모드가 된다.
  - 위젯을 끌어 옮긴다. 브라우저 기본 drag & drop을 쓰고 라이브러리는 추가하지 않는다.
  - 접근성: 각 위젯에 "위로/아래로" 버튼을 둔다. 키보드로만도 옮길 수 있어야 한다.
  - 각 위젯에 "삭제" 버튼, 화면에 "위젯 추가" 목록, "기본 배치로 되돌리기"를 둔다.
  - 크기는 보통·넓게 2단계다. 넓게는 2칸을 차지한다.
- **저장**: 사용자별 배치를 DB에 저장한다. 예: `DashboardLayout(user, widgets JSON)`. 브라우저 저장소에는 두지 않는다. 다른 PC에서 로그인해도 같은 배치가 보여야 하기 때문이다.
- 처음 쓰는 사용자: 역할별 기본 배치를 쓴다(검사원, 승인자, 관리자). 기본 배치 구성은 빌더가 정한다.
- 좁은 화면: 한 줄로 쌓되 저장된 순서를 지킨다.
- 위젯 하나가 오류를 내면 그 위젯만 "불러오기 실패"로 표시한다. 대시보드 전체는 정상으로 뜬다.

## 8. 빌더 검토 후 정한 것 (내 판단, 사용자 확인 대상)

- **기존 부적합의 승인 정보:** 드롭다운으로 승인자를 고른 기존 행은 `approved_at`을 비워 둔다. 비밀번호 서명이 없었는데 서명된 것처럼 보이면 안 되기 때문이다. 대신 "이전 방식 승인" 상태로 본다.
  - 이 상태는 승인 대기·메일 발송 대기 목록에 뜨지 않는다.
  - 삭제는 승인된 기록과 같이 막는다.
  - 처분 규칙(`approved_by` 필요)도 계속 충족한다.
- **승인 뒤 수정 가능한 칸:** 승인된 부적합은 잠그되 다음 칸은 계속 고칠 수 있다. 실패비용, 고객 통보일, `mailed_at`, 후속 링크(CAPA·8D·SCAR)다. 구현은 PPAP의 `AFTER_APPROVAL` 방식(qms/models.py)을 따르고, `Approvable`을 그대로 상속하지 않는다.
- **자동 생성된 부적합의 삭제:** 검사 불합격으로 생긴 부적합은 지금처럼 검사가 남아 있으면 지울 수 없다. 검사가 입력 실수였다면 검사를 먼저 지우고 부적합을 지운다. 삭제 확인 화면에 이 순서를 안내한다.
- **심사 묶음의 PFMEA:** 품번별 승인된 관리계획서(ControlPlan, 품번 FK와 PFMEA 항목 포함)를 출력한다. Document에는 품번 FK를 추가하지 않는다.
- **고객 클레임·반품 유형의 보류:** 다른 유형과 같이 LOT과 하위 LOT을 보류한다. 이미 출하된 수량은 영향이 없고, 남은 재고와 재공품을 막는 것이 IATF 8.7.1이 요구하는 의심품 격리다.
  - 고객 클레임 유형은 CustomerClaim에서 만들 때 자동으로 지정한다.
  - 직접 등록할 때는 CustomerClaim 연결을 요구하지 않는다.

## 9. 통합 업무 플랫폼 요구사항과의 관계

사용자가 함께 준 "통합 업무 플랫폼" 요구사항은 대부분 이미 있거나 이 설계에 들어 있다.
- QMS·MES: 이미 있다.
- 사이드바, 상태 표시, 반응형 화면: §5.11.
- SaaS 기능: §5.12 현장 메모.
- 개인 ERP: §5.13.

빠진 항목은 §2 비목표에 적었다. 외부 SaaS API와 기술 스택 교체가 여기에 해당한다. 위젯 재배치는 §5.14에 들어 있다.

## 10. 열린 질문

없음. 삭제 가능 기간 질문은 §5.1의 관리자 승인 흐름으로 대체되었다.
