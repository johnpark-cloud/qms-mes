# Feature Research

**Domain:** 온프레미스 QMS+MES 기록 화면(통합 상세 화면)과 모듈 라이선스·켜기/끄기 (ISO 9001 / IATF 16949 / AS9100)
**Researched:** 2026-11-12
**Confidence:** MEDIUM — 상용 제품의 화면 배치·라이선스 약관은 대부분 견적제·마케팅 자료라 1차 근거가 약하다. 규제 요건(변경 이력, 전자서명, 인터록)은 HIGH. 화면 관례는 상용 QMS/ERP 공통 패턴에 대한 도메인 지식이며 MEDIUM. 만료 후 읽기 전용 동작은 공개 자료에서 확인하지 못했다(LOW, 아래 「공백」 참고).

승인된 계획(`twinkling-dreaming-lollipop.md`)의 결정은 바꾸지 않는다. 이 문서는 그 결정이 시장 관례에서 어디에 있는지(필수/차별/하지 말 것)를 표시한다.

## Feature Landscape

### A. 모듈 라이선스·켜기/끄기

#### Table Stakes (없으면 제품이 덜 된 것으로 보임)

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| 모듈 단위 구성(문서·CAPA·검사·계측기·심사·클레임·협력사·KPI 등) | QT9, isoTracker, Qualio, SimplerQMS 모두 모듈 단위로 구성·판매한다. 고객은 "필요한 것만 쓴다"를 기대한다 | MEDIUM | 계획 A의 `core/modules.py` 12개 키가 이에 해당 |
| 규격별 패키지(ISO 9001 / IATF / AS9100) 프리셋 | 고객은 모듈 이름이 아니라 "우리 인증 규격"으로 산다. IATF는 PPAP·4M·SPC, AS9100은 형상·FAI가 붙는 것이 관례 | LOW | 라이선스 프리셋(계획 7절). 패키지는 키 묶음일 뿐 코드 분기가 아님 |
| 메뉴·화면에서 꺼진 모듈 숨김 | 안 쓰는 메뉴가 보이면 혼란스럽고 교육비가 늘어난다 | LOW | `visible_nav` + `me_payload.modules` |
| 서버에서 꺼진 모듈 접근 차단(URL 직접 입력, API 포함) | 버튼 숨김만으로는 권한 우회. 심사에서 접근 통제 증거로 쓰인다 | MEDIUM | `module_gate` 미들웨어. URL 전수 매핑 테스트가 누락을 막는 핵심 안전장치 |
| 기존 데이터가 있는 고객은 업그레이드 후 기능을 잃지 않음 | 기록 보존 의무(심사). 라이선스 도입이 기존 고객을 깨면 안 됨 | MEDIUM | 행 추가 전용 데이터 마이그레이션 + reverse. 운영 DB 사본 검증 필수 |
| 라이선스 만료 안내(만료 임박·만료 후 띠 표시) | 갑작스러운 차단은 현장 가동 중단으로 이어진다 | LOW | 만료 N일 전부터 경고 배너. 계획에는 만료 후 띠만 있음 — 임박 경고는 추가 권장 |
| 데이터 접근 보존(만료·비활성이어도 기록은 읽을 수 있음) | 품질 기록은 법정·계약상 보존 대상(IATF/AS9100은 수년~수십 년). 데이터 인질화는 신뢰를 잃음 | MEDIUM | 계획의 「읽기 전용·조회·인쇄·엑셀·백업 허용」 |
| 끄기 전 의존·열린 기록 검사 | 끈 모듈의 미종결 기록이 남으면 고아 기록이 된다. 업무 시스템에서 흔한 "활성 레코드가 있으면 비활성화 불가" 규칙 | MEDIUM | `open_records(key)` + requires 역방향 검사 |
| 시스템 관리자만 모듈 설정 변경 + 변경 이력 | 설정 변경도 감사 증적. 누가 언제 껐는지 남아야 함 | LOW | `ModuleSwitch` + simple-history |
| 백업·복원은 모듈과 무관하게 전체 데이터 | 일부만 백업되면 복원 시 데이터 손실 | LOW | 계획 6절 |

#### Differentiators (경쟁 우위)

| Feature | Value Proposition | Complexity | Notes |
|---------|-------------------|------------|-------|
| 인터록은 모듈 on/off와 무관하게 모델에서 동작(끌 수 없는 부적합·보류) | 핵심 가치("모듈 설정에서도 인터록이 약해지지 않는다")를 구조로 보장. 상용 제품은 모듈 설정과 규칙을 섞는 경우가 많다 | MEDIUM | 업무 규칙은 모델 `clean()/save()`에 두고 모듈 게이트는 접근만 막는다는 분리 |
| 끈 뒤에도 시스템 관리자가 종결 처리 화이트리스트로 열린 기록을 닫을 수 있음 | 풀 수 없는 인터록(deadlock) 방지. 상용 제품 문서에서 거의 다루지 않는 영역 | HIGH | 모듈별 화이트리스트와 그 테스트가 비용. 4M 초품 판정, CAPA 종결 등 |
| 인터록 메시지에 원인 모듈 표시(`[4M 변경] CR-… 초품 검사 합격 전…`) | "왜 막혔는지"를 현장이 바로 알고 문의가 줄어듦 | LOW | 규칙은 그대로, 문구만 |
| 라이선스 만료 시 전체 쓰기 차단·읽기 전용 유지(심사·인쇄·엑셀·백업 허용) | 많은 SaaS는 만료 시 로그인 자체를 막거나 뷰어 좌석만 제공(SimplerQMS 뷰어 라이선스 등). 온프레미스에서 "기록은 계속 볼 수 있다"는 신뢰 요소 | MEDIUM | 로그인·로그아웃·라이선스 교체만 쓰기 예외 |
| 오프라인 서명 라이선스 키(Ed25519, 표준 라이브러리 검증) | 인터넷 없이 검증. 새 의존성 0 | HIGH | RFC 8032 테스트 벡터로 검증. 소스가 고객 PC에 있으므로 코드 수정 우회는 막지 못함 — 위조 키 파일만 막는다는 한계를 문서화 |
| 라이선스(판매사)와 사용 설정(고객 관리자) 분리 | 상용 제품은 한 값으로 섞여 "껐더니 라이선스 풀림" 같은 혼선이 있다. 둘을 곱(AND)으로 판정 | LOW | `active = 라이선스 ∧ 스위치 ∧ 유효` |
| 감사 자료 출력에서 꺼진 모듈 기록을 "(비활성 모듈)" 표시로 포함 | 심사 증거 누락 방지. 모듈 단위 판매에서 놓치기 쉬운 부분 | MEDIUM | `audit_pack` |
| 타임라인·검색에 "비활성 모듈 기록 N건" 한 줄 | 추적성(LOT 계보)이 모듈 꺼짐으로 끊기지 않음 | MEDIUM | 꺼진 모듈 기록을 숨기되 존재는 알림 |

#### Anti-Features (요청은 잦으나 문제가 되는 것)

| Feature | Why Requested | Why Problematic | Alternative |
|---------|---------------|-----------------|-------------|
| 부적합·보류 모듈 끄기 옵션 | "우리는 부적합 안 써요" | 핵심 인터록. 끄면 불량 출하 차단이 사라져 제품의 존재 이유가 무너짐 | 기본 플랫폼으로 고정(계획 확정) |
| 권한 제거로 모듈 숨기기 | 구현이 쉬워 보임 | `ensure_roles`가 migrate마다 권한을 다시 세팅해 덮어씀 | URL·모델 대응표 + 미들웨어 |
| 모듈 행이 없으면 켜짐(기본 켜짐) | 업그레이드 시 편함 | 라이선스 밖 모듈이 열림 | 행 없으면 꺼짐 + 데이터 있는 모듈만 켜는 마이그레이션 |
| 라이선스 만료 시 로그인 차단·데이터 숨김 | 상업적 압박 효과 | 심사·출하 중 가동 중단, 기록 인질화로 법정 보존 의무와 충돌, 고객 신뢰 상실 | 읽기 전용 + 띠 |
| 모듈 끄면 데이터 삭제·숨김 | 화면이 깔끔해짐 | 기록 보존·추적성 위반 | 비활성은 접근만 막고 데이터는 보존 |
| 동시 사용자·좌석 단위 과금 로직 | 상용 제품에서 흔함(QT9 동시접속 등) | 사내 PC 1대~사내망 규모에서 가치 낮고, 좌석 추적은 오프라인 검증과 충돌 | 모듈·패키지 단위만 |
| 하드웨어 지문 바인딩·온라인 활성화 서버 | 복제 방지 | 오프라인 원칙 위배, 서버 PC 교체 시 장애 | 서명 파일 + 만료일 |
| 모듈 개별 가격 세분화(기능 플래그 남발) | 업셀 | 매핑·테스트 폭발. 검사 세부 플래그(`incoming`, `spc`)도 메뉴 숨김에 그친다 | 12개 모듈 + 소수 플래그 |
| 연차·급여(personal)를 판매 패키지에 포함 | 올인원 인상 | 계획에서 제외 확정(코드·데이터는 유지) | 내부 전용 키 `personal` |

### B. 통합 기록 상세 화면(머리 띠 + 오른쪽 열)

#### Table Stakes

| Feature | Why Expected | Complexity | Notes |
|---------|--------------|------------|-------|
| 머리 띠: 기록 번호·제목·상태(판정/처분/승인 상태) 상시 노출 | QMS/ERP 레코드 화면의 공통 문법. 사용자는 "이 기록이 지금 어떤 상태인가"를 먼저 본다 | MEDIUM | `RecordSpec.status(obj) -> {label, tone}`. 색+글자 병행 |

| 첨부 파일 | 사진·성적서·증빙. 모든 QMS 기록에 있음 | LOW | 기존 `AttachmentPanel` |
| 메모·코멘트 | 협업 기본 | LOW | 기존 `MemoPanel` |
| 승인 서명(비밀번호 재입력)과 승인 후 잠금 | 전자서명 관례. 서명은 사용자·시각·의미(승인/반려)를 기록 | MEDIUM | 기존 `SignModal`, `ApprovalAdminMixin` 재사용 |
| 잠긴 기록의 수정 요청·삭제 요청 흐름 | 승인 후 변경은 통제된 절차로 | MEDIUM | 기존 흐름 연결(B2) |
| 인쇄/PDF·엑셀 출력 | 심사·고객 제출용 | LOW | 기존 `ReportLinksMixin` |
| 권한 없는 사용자에게 서버 측 거부 | 화면 숨김만으로는 우회 가능 | LOW | `require_perm` |
| 모델 검증 오류를 칸별 메시지로 표시 | 편집 화면 기본 UX | MEDIUM | `full_clean` → 필드별 오류 매핑 |

| 다크·라이트, 좁은 화면(390px)에서 오른쪽 열이 아래로 | 현장 태블릿·모니터 환경 | LOW | 토큰 + CSS |

#### Differentiators

| Feature | Value Proposition | Complexity | Notes |
|---------|-------------------|------------|-------|
| 서버 기록 설명서(`RecordSpec`) 하나로 28종 화면 생성 | 모델 추가 시 설명서 한 건이면 화면·목록·API가 생긴다. 상용 제품은 화면별 개발이 일반적 | HIGH | B1 핵심. 사용자 정의 칸(`extra`)을 FieldDef에서 자동으로 칸화(B6) |
| 검사 결과 화면: 판정 띠 + 측정값 표 + 공차 위치 막대 | 숫자만 나열하는 표보다 공차 대비 위치(치우침·한계 접근)가 즉시 보임. 상용 SPC/QMS에서도 있으나 기록 화면 안에 표준 컴포넌트로 있는 경우는 드묾 | MEDIUM | 하한~상한 점 표시, 양끝 10% 주의색, 한쪽 규격이면 막대 숨김 |
| 판정 띠 전용 큰 글자(28px) + 색+글자 병행 | 합격/불합격을 3초 안에 인지. 색각 이상 대응 | LOW | DESIGN.md Lead 토큰 |
| 한 곳에만 있는 삭제(「⋯」 메뉴), 주요 버튼 1개 | 중복 삭제 버튼·값처럼 보이는 인쇄 링크 제거(현재 지적) | LOW | 버튼 규칙 공통화 |
| 기록마다 같은 틀 → 학습 비용 0 | 교육 시간 절감. 품번·검사기준·관리계획서도 같은 틀 | MEDIUM | `RecordPage` 겉모양 교체(props 계약 유지) |
| 처분 서명 전용 본문(MRB 비밀번호), 보류는 읽기 전용 | 핵심 인터록 규칙을 화면에서도 약화 없이 그대로 | MEDIUM | B3 |
| 기존 관리 화면에서 「새 화면으로」 링크, `/admin/`은 뒷방 유지 | 전환 위험 최소, 북마크 보존 | LOW | 템플릿만 수정 |
| `record_url` 단일화로 검색·타임라인·종합현황 링크가 자동으로 따라감 | 화면 이전 시 링크 깨짐 방지 | MEDIUM | 7개 파일 + `core/views.py` 반환 주소 |

#### Anti-Features

| Feature | Why Requested | Why Problematic | Alternative |
|---------|---------------|-----------------|-------------|
| 기록별 완전 맞춤 레이아웃(화면마다 다른 배치) | 도메인별 최적화 | 28종 유지 불가, 학습 비용 증가 | 공통 틀 + 전용 본문 슬롯(검사·처분만) |
| 사용자가 화면 레이아웃을 직접 편집(드래그·섹션 숨김) | 상용 플랫폼형 QMS 기능 | 검증(Validation)·교육·지원 부담, 설명서 방식과 충돌 | 서버 설명서로 고정, 사용자 정의는 `extra` 칸까지만 |

### Dependency Notes

- **module_gate는 대응표 완결성에 의존한다:** 누락된 URL은 꺼진 모듈이 열리는 구멍이다. 그래서 URL 전수 테스트가 먼저 있어야 한다.
- **records API(B1~)는 A1 이후 대응표에 등록해야 한다:** 범용 경로(`/api/records/<app.model>/`)는 kwargs의 모델로 판정하는 일반화 URL 규칙에 들어간다. 새 범용 쓰기 API가 게이트를 거치지 않으면 꺼진 모듈 기록을 수정하는 우회로가 된다. 순서 B0 → A1~A4 → B1~B6이 이 충돌을 피한다.
- **편집 모드는 만료 읽기 전용과 충돌 가능성이 있다:** B2 범용 쓰기 API가 만료 판정 미들웨어를 반드시 통과해야 한다. 테스트에 "만료 + 범용 저장 → 거부"를 넣는다.
- **종결 화이트리스트는 records API의 범용 쓰기와 별개로 정의한다:** 꺼진 모듈에서 허용되는 쓰기는 "종결 처리"뿐이므로 범용 `PUT`은 허용하지 않는다.
- **RecordShell은 모든 B 단계의 선행:** B0에서 먼저 만들고, 이후 단계는 설명서만 추가한다.
- **인터록 메시지 원인 표시는 모듈 판정과 모델을 연결한다:** 규칙 변경이 아니라 문구 변경임을 테스트(기존 인터록 테스트 전부 통과)로 확인한다.

## 공백(후속 단계에서 확인)

- 상용 제품이 라이선스 만료 후 읽기 전용을 어떻게 처리하는지 공개 자료로 확인하지 못했다. 이 문서의 「일반적으로 만료 시 로그인 차단 또는 뷰어 좌석 제공」은 LOW 신뢰. 계획의 읽기 전용 방식은 보수적이고 기록 보존 관점에서 안전하므로 결정에는 영향이 없다.
- 상용 QMS 기록 화면의 정확한 배치 표준은 없다. 「머리 띠 + 오른쪽 열」은 사용자가 이미 선택한 안이고, 요소 구성(상태·기본정보·하위 표·관계·첨부·메모·이력·서명)이 시장 필수 요소와 일치한다는 점만 확인했다.
- 모듈 끄기 전 열린 기록 검사의 모듈별 「열린」 정의(예: 열린 작업지시, 미판정 검사)는 도메인 전문가 확인이 필요하다. A3 단계 연구 후보.
- 만료 후에도 허용할 쓰기 예외(예: 종결 처리, 백업 복원)는 현재 로그인·로그아웃·라이선스 교체뿐이다. 만료 중 열린 부적합 처분이 필요한 경우를 A2에서 확인해야 한다.
