# QMS+MES+ERP(일부) 전체 데이터 확장 설계

- 작성일: 2026-11-11
- 상태: 방향 승인됨(2026-11-11). 단계별 상세는 각 단계 계획 문서에서 확정한다.
- 근거:
  - 사용자가 보낸 개발 단계 그림(①요구사항 분석 ~ ⑳모니터링)
  - 계측기 항목 표(2-1~3-3)
  - 사용자 지시: 회사 양식은 없음, AS9100 포함, 최종 형태는 QMS+MES+일부 ERP 패키지, 매뉴얼·절차서·지침서와 심사 대응 포함
- 항목은 ISO 9001:2015, IATF 16949:2016, AS9100D, ISO 10012, AS9102의 일반 관행으로 만든 **초안**이다. 조항 번호는 회사가 가진 규격 원문으로 확인한다.

## 1. 최종 형태

한 패키지 안에서 아래를 모두 다룬다.

- **QMS**
  - 문서 체계: 매뉴얼 → 절차서 → 지침서 → 양식 → 기록
  - 품질 기록과 심사 대응
- **MES:** 작업지시, 라우팅, 실적, LOT 계보, 설비, 특수공정
- **ERP 일부:** 구매(발주·입고), 영업(수주·출하), 재고(입출고·현재고)
  - 회계·원가·인사급여는 범위 밖이다. 개인 연차·급여 화면은 있지만 ERP 인사 모듈은 아니다.

심사 대응의 목표는 다음과 같다. 심사원이 "이 조항의 근거를 보여 달라"고 하면 조항 → 절차서 → 실제 기록까지 화면 한 번에 찾아 출력한다.

## 2. 왜 하는가

현재 모델은 기록 칸이 너무 적다. 2026-11-11에 실제로 센 결과는 다음과 같다.
- 품번 3칸, 공정 2칸, 계측기 6칸, 검사 6칸
- 문서 3칸(번호, 제목, 종류)

협력사·고객사·심사원·피심사 부서는 글자 칸이다. 해당 칸은 다음과 같다.
- `Lot.supplier`, `Shipment.customer`
- `Scar.supplier`
- `CustomerRule.customer`, `CustomerClaim.customer`, `PpapSubmission.customer`
- `InternalAudit.auditor/auditee`

그래서 같은 거래처가 여러 이름으로 갈라지고 집계를 믿을 수 없다. 기준정보를 먼저 세우고, 그 위에 모듈을 넓힌다.

## 3. 원칙

- 기존 데이터는 지우지 않는다. 새 칸은 비어도 되는 칸으로 추가한다.
- 기존 글자 칸은 남기고, 옆에 연결 칸을 둔다.
  - 기존 글자 값을 새 기준정보에 연결하는 정제는 **사용자가 승인했다(2026-11-11)**.
  - 정제는 이름이 정확히 같을 때만 연결한다. 연결하지 못한 값은 목록으로 보고한다.
  - 실행 전에 `backup`을 실행한다.
- 필수 항목은 새로 등록하거나 고칠 때부터 `clean()`에서 강제한다. 옛 기록의 열람과 출력은 막지 않는다.
- 보호 규칙(LOT 보류, 교정 인터록, 검사 판정, 승인 서명, 본인 열람)은 약하게 만들지 않는다. 강하게 만드는 변경도 단계 계획에서 따로 표시한다.
- 새 모델은 다음을 따른다.
  - `history = HistoricalRecords()`, 한국어 `verbose_name`, `BaseAdmin`을 쓴다.
  - 삭제는 시스템 관리자만 한다.
- 거래처·부서 편집은 품질팀장과 시스템 관리자만 한다(**사용자 승인 2026-11-11**). 다른 역할은 열람만 한다.
- 작고 간단하게 만든다(**사용자 지시 2026-11-12**): 관리·사용은 단순하게, 업무 칸은 빠짐없이. 코드 추가는 표에 한 줄 붙여 넣기로 끝나야 한다.
- 화면은 탭으로 나눈다(기본 / 상세 / 첨부 / 이력). 기본 탭의 필수 칸만 채워도 저장된다.
- 새 의존성은 넣지 않는다. 오프라인에서 동작해야 한다.

## 4. 그림의 단계와 이 시스템 (뼈대)

사용자가 해야 한다고 정한 단계는 ②③④⑤⑦⑧⑨⑩⑪이다(2026-11-12). 각 단계의 뼈대는 아래와 같다.

| 단계 | 뼈대 | 상태 |
|---|---|---|
| ①② 요구사항·핵심기능 | 이 문서 5~7절, 모듈 순서는 10절 | 있음 |
| ③ 아키텍처 | Django(규칙·관리 화면) + DRF `/api/` + React `/app/`. 앱은 `core`·`qms`·`personal`. 8절 | 있음 |
| ④ 인프라·보안 | waitress, whitenoise, `backup`/`restore`, 역할 권한(`ensure_roles`), 승인 서명, simple-history | 있음 |
| ⑤⑦ 데이터 연동·공통 API | `core/api` 방식(권한 검사·오류 형식). 모듈마다 같은 방식으로 API를 붙인다 | 있음, 모듈마다 추가 |

| ⑩ 문서 저장소 | `data/` 첨부 폴더와 공통 첨부 `Attachment` | 있음 |

| ⑫~⑮ Graph DB·RAG·LLM·Agent | **하지 않는다(사용자 결정 2026-11-11)** | 범위 밖 |
| ⑯ 프론트엔드 | React `/app/` |
| ⑰ 업무 시스템 연동 | QMS·MES·ERP를 한 DB 안에서 연결한다. 외부 ERP 연동은 대상이 정해지면 한다 |
| ⑱ 통합 테스트·보안 | `manage.py test`, `e2e_check.py`, `e2e_browser.py` |
| 파일럿 → ⑲ 단계 배포 → ⑳ 모니터링 | 7절 단계마다 배포한다. 문제가 있으면 개선한 뒤 다시 시험한다 |

## 6. A단계 항목 상세 (구현됨, 커밋 6cb0fb6)

표기: **필**=필수, 권=권장, 조=조건부, 선=선택.

사업장·직원·거래처 담당자 표는 두지 않는다(사용자 결정 2026-11-12). 조직은 부서 조직도로만 관리한다. 아래 거래처 칸 중 실제 구현은 최소 칸(구분·상태·품질 담당자 1명·인증서)이다. 정확한 칸은 `core/models.py`의 `Partner`가 기준이다.

**부서 `Department`**
- 코드 **필**, 이름 **필**, 상위 부서 선, 부서장(사용자) 권, 사용 **필**

**거래처 `Partner`**
- 기본: 코드 **필**, 상호 **필**
- 구분 **필**: 협력사 / 고객사 / 외주가공 / 교정기관 / 기타 중 하나 이상
- 사업자등록번호 권, 대표자 선
- 연락: 주소 권, 대표전화 권, 이메일 선, 담당자 이름·전화·이메일 권
- 품질:
  - 거래 상태 **필**: 신규 평가 / 승인 / 조건부 승인 / 거래 중지
  - 품질인증 선: ISO 9001 / IATF 16949 / AS9100 / ISO 17025 / 기타
  - 인증번호 선, 인증 유효기한 조(인증이 있을 때)
  - 최근 평가일 선, 평가 등급 선
- 비고 선, 사용 **필**
- 상태를 "승인"으로 바꾸는 것은 품질팀장·시스템 관리자만 한다(편집 권한과 같다).

**공통 첨부 `Attachment`**
- 대상(모델·행) **필**, 종류 **필**(사진 / 사양서 / 매뉴얼 / 구매서류 / 성적서 / 보증서 / 인증서 / 기타), 파일 **필**, 설명 선
- 올린 사람·일시는 자동이다.
- 열람 권한은 대상 기록의 열람 권한을 따른다.

**연결 칸 추가(정제 대상)**
- `Lot.supplier`, `Scar.supplier` → 협력사
- `Shipment.customer`, `CustomerRule.customer`, `CustomerClaim.customer`, `PpapSubmission.customer` → 고객사
- `InternalAudit.auditee` → 부서
- 글자 칸은 남긴다. 화면은 연결 칸을 우선 보여 준다.

## 7. 단계 순서

각 단계는 계획 문서 → 구현 → 테스트 → 배포 순으로 하고, 단계마다 따로 배포할 수 있다.

| 단계 | 내용 |
|---|---|
| A | 기준정보: 부서·거래처·공통 첨부, 연결 칸과 정제, 화면·엑셀 등록 (구현됨) |
| B | 문서 체계: 문서 등급(매뉴얼/절차서/지침서/양식/외부), 소관 부서, 관련 조항, 시행일, 검토 주기·다음 검토일, 배포·회수, 폐기본 표시, 읽음 확인. 기록 보존기한 |
| C | 심사 대응: 규격 조항 마스터(ISO 9001, IATF 16949, AS9100D, 고객 CSR), 조항↔문서↔기록 매트릭스, 외부심사·지적사항, 심사 증적 묶음 출력 |
| D | 공급자·수입검사: 승인 협력사 품목, 공급자 평가(품질·납기), 공급자 감사, 하향전개 요구, 위조품 방지 확인. 입고 LOT·수입검사 칸 보강 |
| E | 계측기: 사용자 표 2-1~2-7, 교정 이력(3-1), 수리 이력(3-2), 교정 불합격 시 영향 기록 회수(AS 7.1.5.2), MSA 기록 |
| F | 품번·공정·설비: 품번·공정 보강, 설비·금형, 예방보전 |
| G | 제품 실현 강화: FAI(AS9102), 핵심특성, 형상관리, 특수공정, FOD, 제품 안전 |
| H | 교육·역량, 리스크 등록부, 품질목표·경영검토, 고객만족·OTD |
| I | ERP 일부: 수주, 발주·입고, 재고 |
| J | MES 강화: 작업표준 연결, 작업자 자격 확인, 비가동, 재작업 |

변경 이력(표 3-3)은 simple-history가 이미 남긴다. 변경 사유는 기존 수정 요청(`RevisionLog`) 흐름을 쓴다.

## 8. 구조

- A단계 모델(부서·거래처·공통 첨부)은 `core` 앱에 둔다. 모든 앱이 쓰기 때문이다.
- 품질 모듈은 `qms`, 생산 모듈은 `core`의 생산 모델 옆에 둔다.
- ERP 모듈의 앱 위치는 I단계 계획에서 정한다. 새 앱을 만들면 앱 경계 변경이므로 그때 묻는다.
- 권한은 `ensure_roles`에 새 모델을 추가한다. 역할 표는 각 단계 계획에 적는다.
- API는 `core/api` 방식을 따르고, 화면은 React 메뉴에 넣는다. 단순한 표 마스터는 `TablePage`, 칸이 많은 마스터는 탭 상세 화면을 쓴다.

## 9. 범위 밖

- ⑫~⑮ AI 기능(사용자 결정 2026-11-11). ⑪ Vector DB는 자리만 마련한다(4절).
- 외부 ERP 연동, 회계·원가

## 10. 모듈 순서 (사용자 결정 2026-11-12)

뼈대 위에 모듈을 하나씩 끝내고 합친다. 각 모듈은 설계 → 계획 → 구현 → 테스트 → 커밋 순으로 한다.

| 순서 | 모듈 | 내용 |
|---|---|---|
| M0 | 공통 입력 틀·모듈 켜기/끄기 | 코드값·부서·거래처를 표 화면(엑셀 붙여 넣기)으로 옮긴다. 모듈 켜기/끄기는 시스템 관리자만 바꾸고, 서버에서 막고, 이력을 남긴다. 권한 변경이므로 설계 때 승인을 받는다 |
| M1 | 계측기·교정 | 7절 E단계. 화면과 필요한 칸(사용자 표 2-1~3-2), 교정 불합격 영향 회수 |
| M2~ | 나머지 | 7절 B·C·D·F~J 순서는 M1 뒤에 다시 정한다 |
